# 漂移裁决口径（`scripts/check_drift.py` 的红怎么读）

哨子（drift sentinel）比对「仓里的源」与「市场现行版」。它每天要回答的不是「有没有差异」，
而是**这份差异该谁动、往哪个方向动**。方向搞反的代价不对称：仓落后时发布＝拿旧版盖线上，
仓领先时不出片＝白改。

2026-11-13 之前它只会说 `漂移 keys=['i18n']`，于是每处差异都得人另写脚本剥两层才看清——
一天里就因此误判过一次（把「市场多三个语种」当成「两边各改过」）。

现在每条红都带一句方向结论。四类，处置各不相同：

| 结论 | 判据 | 处置 | 为什么不能反过来做 |
|---|---|---|---|
| **仅显示副轨差异** | 正文（除 `i18n` 的整份 manifest）两侧逐字一致，只有 `i18n` 有差 | **从市场回填 `i18n`**，然后在同一提交里回填台账版本格 | 中文源一致 ⇒ 这不是内容分歧，是译文落后。反过来「重铸发布」会把译文回退成更短的那版 |
| **仓库严格落后** | 差异里没有「仅仓库有」也没有「两侧都不同」，全是「仅市场有」 | **别发布**；先从市场把缺的键回填进仓 | 从仓发布会把市场多出来的内容整段删掉（实测过一次：某包 `fleet` 2075B→1639B） |
| **仓库严格领先** | 差异里没有「仅市场有」也没有「两侧都不同」，全是「仅仓库有」 | 出片候选：核这份改动是不是要的，是则重铸→发布 | 不出片等于白改；但**必须人核**，因为「仓里有」也可能是误提交 |
| **同键异文 / 双向分叉** | 两侧都存在但值不同，或两边各有领先 | **禁止任一侧直接覆盖**；逐字段人工裁决 | 任一侧覆盖都会丢东西。同键异文常见成因：源改了、市场那版是旧的中文；或市场手工改过 |

## 两个先决问题（判据建立在这上面）

1. **方向不靠版本号判，靠内容判。** 台账版本格可能是陈旧的（今天清掉 10 处），所以
   「市场 v9 > 台账 v7」不能推出「仓落后」。
2. **`i18n` 必须摘出来单独看。** 顶层 `i18n` 两侧都存在时，原来的 `keys=[…]` 会把
   「仓里只有 en、市场有 en/es/fr/ja」说成「两侧都不同」——方向恰好相反。
   `--detail` 可逐叶子打印两侧的值。

## 源缺失 ≠ 漂移

`源缺失` 是第三种故障：台账记了源，仓里/工作区里找不到。三种成因，输出会点名查过的根：

- **根找错**：本仓可能是工作区之外的 worktree，`REPO.parent` 不再等于工作区根；
  由 `workspace_roots()` 的候选链处理（`FP_WORKSPACE_ROOT` 可显式指定）。
- **源在兄弟仓**：ERP 模板包住在 `fd-erp-vertical-templates/`，不是本仓。
- **源从未进过版本控制**：2026-11-13 查出 7 个已发布包的源只以未跟踪文件躺在某个工作树里
  （任何分支 0 提交）。这类必须先纳入版本控制，否则一次磁盘故障就是永久丢失。

## 重铸不是万灵药

`cast_fleet_template.py --check` 能回答另一个问题：**仓里的 manifest 是否与它自己的源一致**。

- `CHECK OK` → 仓内自洽；与市场的差异是「未发布的改动」。
- `CHECK FAIL` → manifest 与源不一致。注意方向：可能是 manifest 落后于源（重铸即可），
  也可能是**源落后于 manifest**（重铸会删内容，见 hotel/industry-watch-fleet）。
  判据：看重铸产物比原文件**小**还是大——小就说明原文件有源产不出的内容，别重铸，先补源。

铸造工具现在的顺序纪律：注册处校验前置，prevalidation 失败会把原字节写回——
**失败的铸造不留副作用**。
