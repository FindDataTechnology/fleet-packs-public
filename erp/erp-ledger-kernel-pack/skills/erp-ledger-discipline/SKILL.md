# ERP 复式账本内核纪律卡

本卡是 `fd-erp-ledger-mcp`（ERP 板块，本位币 CNY）的如实口径守界，供集群岗位与 cell 复用。以下每条都是真实能力边界，不得对外宣称越界能力。

## 一、写路径只有 proposal，确认门才入账
- agent 与外部调用方只能提交 proposal（拟入账事件），proposal 不直接改变账本状态；没有任何绕过确认车道的直写落账工具。
- 确认门（confirm_proposal）是入账的单一关口：确认后按复式分录入账；借贷必平由数据库约束触发器强制，不平则整笔拒绝。
- 拒绝（reject_proposal）留审计痕迹且不入账；stable_id 幂等去重，同键重复提交返回首次结果（唯一索引落库）。

## 二、已入账分录只进不改
- 已入账分录 append-only：任何更正以冲正（反向/红字分录）表达并与原分录关联可溯；改/删路径不存在（数据库拒）。
- 余额按科目/币种查询，由分录确定性重算，无独立余额字段；每条分录带来源引用与时间戳。

## 三、对账引擎只读滩头
- 两源流水对齐，产出四类差异（缺失、多余、金额不符、状态不符），每条含双侧原始引用，报告落档可查。
- 对账阶段对客户外部系统保持只读、零数据改动，不要求客户更换既有经营系统；长任务立即返回 task_id，状态与进度可查。

## 四、多币种与凭证
- 原币 + 本位币折算（汇率 + as_of + 出处）；无出处汇率拒绝。
- 租户列隔离 + 查询闸：跨租户查询拒绝并审计留痕；BYOK 凭证经环境变量注入，零落库零日志。

## 五、工具面是八组三十二件（按组理解，不逐条背）

工具面的单一出处是内核仓的 `tool-surface.json`；逐工具的说明书在内核仓 `toolkit/`——八张工具卡，一组一张，外加一份机器可读目录，回答「这组能做什么、不许做什么、硬纪律是什么、哪类岗位调哪几件」。本卡只交代分组与授权分层：

- **proposal（4 件）**：拟落账事件车道。agent 写路径的入口；确认门与否决门同组，但那是人的动作，只给拍板岗。
- **ledger（2 件）**：账本只读面。余额与分录都从这里读；余额是分录的重算结果，不存在可写余额。
- **recon（2 件）**：对账只读滩头。发起长任务与取报告，对外部系统零写入。
- **billing（9 件）**：计费规则引擎。规则版本化 + 人工审批上线 + 冲突拦截 + 事件/期间快照计费 + 红冲留痕 + 四层溯源 + 无出处费率拒绝 + 试算零写入；费用落账走机器车道 proposal。
- **credit（4 件）**：信用额度。可用额度由上限、应收余额与有效占用派生；占用是备忘性质，不写复式分录。
- **event（4 件）**：业务事件层。两条车道——导入车道写入即事实，拟稿车道未过事实确认门不算事实；事件只追加，定型后不可改写，更正只走冲正。
- **object（2 件）**：数量面（对象投影）。库存、在途、占用的余额由事件确定性重算并带水位；余额是投影产物，不可直写。
- **posting（5 件）**：过账层。已接受事件经版本化规则确定性映射为分录；规则须审批上线、同事件类型仅一条生效、升版不重写历史；缺规则不猜科目，事件挂待补清单、余额不变。

三层的授权边界与工具书同一口径：巡检层只调只读面；核对层可读全组、可提交 proposal / 拟稿事件 / 规则草稿，不持确认门；拍板层独占确认门与审批门（确认 proposal、裁决拟稿事件、审批计费规则与过账规则）。**岗位边界就是工具权限边界**——包级白名单只作封顶，真正生效的是逐岗收窄。

## 六、未知必须显式，如实计量
- 未提供或未知的金额、币种、出处一律显式标未知；空串、零、空数组会被下游读成「确实为零」，与「不知道」不可区分，载荷校验会直接拒绝空值。
- 拿不到证据就说明拿不到（NOT_WIRED），不掷骰子、不猜数量、不以人工补录冒充自动接入。
- 每次响应含 rows_returned 计量戳；错误为封闭错误码集合，不伪装空成功；结果统一体积上限，超限给截断标记与分页续读，截断结果不得当成全部。

## 七、合规红线（如实守界，不得宣称越界能力）
- 资金归集/代收代付/分账：平台只做对账与核对指令层，资金走客户自选持牌通道（二清红线）。资金类科目不在机器车道白名单内，任何岗位都不把它们写成可写。
- 开票/税务申报不自研（挂账）；账内可记录发票类事件并参与对账，票据本体由客户既有合规渠道处理。
- 不宣称：单体 ERP 应用/表单 UI、开票自研、资金执行、网关已上线、市场已 live 上架、registry 快照已 live 写入。
